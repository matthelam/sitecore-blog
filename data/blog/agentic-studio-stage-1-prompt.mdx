Most people's first agent is a chat box and a well-written prompt. That turns out to be a better start than it sounds, and a worse place to stop.

**Prompting well is the first skill of agentic engineering, and a good prompt gets real work done. Its limits show when you need the work done the same way every time, and done right without checking it yourself.**

This is the first of five posts. Each one builds the same SEO agent in Sitecore Agentic Studio, with more machinery each time.

## One task, five stages

The series does two jobs at once. It's a hands-on reveal of Agentic Studio's building blocks, one set at a time: the bare chat, then brand kits and context, then a standard agent with tools and a scorer, then a workflow agent that loops, then a graph of agents across many pages. And it puts something concrete behind the stages of agentic engineering everyone talks about: prompts, context, harnesses, loops and multi-agent graphs.

The constant is the task. One page, one question, five SEO fields, the same pass bar and the same independent score at every stage. Only the machinery around the task changes, so any difference in effort, quality or consistency comes from the stage, not the job.

Each stage is named for the one quality it adds.

## The example: a bouldering gym that doesn't exist

The page belongs to matthelam Boulderfest, a fictional Adelaide bouldering gym. The agent's job is to tune the SEO of one page, `/climb/casual-entry`, so that a search engine or AI answer engine cites it for one question:

> How much does a casual bouldering session cost in Adelaide?

Five fields are in scope: page title, meta description, Open Graph title, Open Graph description and JSON-LD structured data. They start deliberately weak, so there's something to improve. The title and Open Graph title say "Casual entry", and the other three are empty. The only facts allowed are the ones the page states: adults \$28, concession \$24, under 15 \$20, shoe hire \$6, free chalk, a 10-visit pass for \$250, a five-minute safety induction and six zones.

The independent score comes from [seo-jev-analyzer](/blog/seo-jev-analyzer), my own open-source scorer. It rates ten expected terms for how central they are, multiplies that by how fully the page answers the question, and gives a score from 0 to 10. At stage 1 it sits outside the chat. I run it on the live page before and after, and the chat never sees the result.

Stage 1 is what most people do first: Agentic > Chat > New chat, and type. Nothing is configured, so every rule, fact and check has to live in the prompt, or in my head.

## Doable: a good prompt gets real work done

**A model is a reasoning engine, and in Agentic Studio the tools are already within reach.** I didn't tick a single tool. Studio's built-in tools (Sites, Content, Pages and Web Search) were available anyway, and the chat called them by itself.

From seven plain-English prompts, it found the page, searched the web for Google's current guidance on titles, descriptions and structured data, and graded each field. It then drafted all five with valid JSON-LD, wrote them to the CMS behind Studio's own Apply changes card, and read them back. No agent, no configuration.

The recommendations were ok. Not brilliant, ok. From the true starting values, seo-jev-analyzer's metadata score went from 0.00 to 1.96, and the page score from 4.11 to 4.83 (three runs each). The gain is modest, and the reason is telling: the chat never saw the ten terms the scorer expects. A rewrite aimed at those terms scored 4.12 on metadata, roughly twice as high.

| Version of the five fields                | Metadata | Page |
| ----------------------------------------- | -------- | ---- |
| Starting values                           | 0.00     | 4.11 |
| What the stage 1 run wrote                | 1.96     | 4.83 |
| A rewrite aimed at the ten expected terms | 4.12     | 5.28 |

### What the prompts did well

{/* AUTHOR TO CONFIRM: which of these habits Matt claims as the craft, and anything to add. */}

Looking back over the seven prompts, these are the habits doing the work:

- **A role.** "Act as an SEO specialist."
- **The goal as an outcome, not a task.** "Be the page a search engine or AI answer engine cites when someone in Adelaide asks how much a casual bouldering session costs."
- **Exact fields and an exact output shape.** The five fields by name, a table with character counts, and the JSON-LD in a code block.
- **A way to say "I don't know".** "Write EMPTY for a field that exists with no value and NOT RETURNED for a field your tools did not give you." Some tools leave fields out, and without this the chat fills the gap with a guess.
- **Rules with numbers.** A title of 60 characters or fewer, a description of 150 to 160, ending with the site name.
- **Facts bounded to the source.** "Use only prices, times and facilities from the page."
- **The job in rounds.** Get, analyse, suggest, review, apply, re-check, with "do not change anything" in every round until the one that applies.
- **A review round that names its checks.** Asked to recount, the chat cut the description from 161 characters to 157, back inside the rule.

So a plain chat gets a long way. The trouble is that it doesn't get there the same way twice.

## Inconsistent: same prompt, different work

**The same prompt, sent twice, can produce different work, and the chat can't reliably tell you when its own work is wrong.** None of this shows in a single run. It shows across runs.

**It picks its own tools.** In the recorded run, Round 1 used seven tools nobody asked for: tool search, list sites, search pages, get page, get page metadata, get page content and get page HTML. Another run of the same prompt chose a different set. Different tools return different fields, ask for approval differently and write by different routes. I saw this in every run, but I haven't tested how often each path comes up.

**It misses things.** In my experience, about one run in ten doesn't pick up some of the fields it was asked to analyse.

**It gets lazy in a long session.** Run it too many times in the same chat and it starts reusing data from earlier instead of fetching it again.

**Nothing tells it which fields matter.** The Boulderfest page item carries two sets of SEO fields. One set is rendered on the live page; the other isn't. The prompt names the fields, and the chat decides which set they mean. In Round 6 it read the set that isn't rendered, saw an empty description and called its own result "partial". The live page was serving every new value.

The title, "Casual Bouldering \$28 in Adelaide | Boulderfest", fared worse: Round 3 counted 44 characters, and the recount said 46. **Guardrails are requests, not checks.** "Do not guess", "do not invent anything", "check your proposal against every rule": the model acts on them as it chooses, and nothing confirms it obeyed.

**Warnings slip past.** The Apply changes card appeared because of the tool the chat happened to pick; with another tool it asks in words instead. After the save, Studio reported that the changes "could not be fully applied". The run treated the save as done. A person reading quickly would too.

Doable, yes. The same way every time, no.

## Tedious: the price of reliability by hand

**Nothing in a plain chat makes the result reliable, so the person does it, every time.**

Look at the prompts again and a good share of the text isn't the task. It's guardrails: what the chat can and can't do, don't guess, don't change anything, check your work. The same lines go into prompt after prompt, because a plain chat has nowhere else to keep them.

The panel kept count: 7 prompts sent, 443 words written by hand, 10 operator actions and 8 minutes, for one page. Take the operator away and the process stops. That's the figure the next four stages have to beat.

## What stage 2 changes, and what it doesn't

Stage 2, Context, moves the facts and house rules out of the prompt and into a brand kit the chat reads every time: the page's goal, the prices, the title and description rules, the expected terms, and which fields are rendered. It's aimed squarely at the facts that lived in my head and at the question of which fields matter. Context comes first because it improves the output itself: the expected terms are what the score rewards.

It won't make stage 1 repeatable or reliable. The chat will still choose its own tools and mark its own work. Repeatability arrives with the harness at stage 3, and reliability with the loop at stage 4.

## What I'd change on the next take

- Name the rendered fields in every prompt, so the chat can't pick the wrong set.
- Check the starting values on the live page, not in the chat's reply.
- Treat "could not be fully applied" as a failed step, not a pass.

A prompt is where agentic engineering starts, and prompting well can get you a long way. Its limits show when you need the work done the same way every time, and done right without checking it yourself. Stage 2 starts moving that weight out of the prompt.
