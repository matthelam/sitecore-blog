**Prompting well is the first skill of Agentic Engineering, and it's amazing how much you can get done if you're willing to just try a prompt and see. Its limits show when you need the work done the same way every time, and done right without checking it yourself.** We'll follow one working example through each stage of Agentic Engineering, and see how each stage improves the process.

## One goal, five stages

This post starts a series on building agents in Sitecore's new Agentic Studio. Each post repeats the same SEO optimisation task, adapted to show what one stage of Agentic Engineering looks like. If you're new to AI, these stages are a popular way to describe the journey many people have taken as they discover the complexities of this latest form of AI.

Every stage works on the same page, question and five SEO fields, and is scored the same way. The steps change as each stage brings in more of Agentic Studio's functionality, so any difference in effort, quality or consistency comes from the stage itself.

Each stage is named for the one quality it adds.

## Scenario

We run a website called matthelam Boulderfest, for a fictional Adelaide bouldering gym. The agent's job is to tune the SEO of one page, `/climb/casual-entry`, so that a search engine or AI answer engine cites it for one question:

> How much does a casual bouldering session cost in Adelaide?

Five fields are in scope: page title, meta description, Open Graph title, Open Graph description and JSON-LD structured data.<InfoTip label="Why these five fields?" title="Why these five fields" body={["Stage 1 sticks to this metadata because the tooling is more basic and easier to manage. Later stages widen the work and learn to manage multiple tools.", "The metadata is also the page's first impression for people and agents. Search engines read the whole page, but the title and description shape the result people and agents choose from.", "Bing says weak titles and meta descriptions can reduce a page's 'eligibility for grounding results and citations' in Copilot, and that structured data 'may support clearer grounding'."]} links={[{ label: 'Bing Webmaster Guidelines', href: 'https://www.bing.com/webmasters/help/webmaster-guidelines-30fba23a' }, { label: 'Google: title links', href: 'https://developers.google.com/search/docs/appearance/title-link' }]} /> They start deliberately weak, so there's something to improve. The title and Open Graph title say "Casual entry", and the other three are empty. The only facts allowed are the ones the page states: adults \$28, concession \$24, under 15 \$20, shoe hire \$6, free chalk, a 10-visit pass for \$250, a five-minute safety induction and six zones.

An independent score comes from [seo-jev-analyzer](/blog/seo-jev-analyzer), my own open-source tool, which rates the page from 0 to 10 on how well it answers the question. At stage 1 it sits outside the chat, so I have to run and check it manually on the live page, before and after. The chat never sees the result.

Stage 1 is what most people try first. You open Agentic > Chat > New chat and type. Nothing is configured, so every rule, fact and check has to live in the prompt.

## Doable: a good prompt gets real work done

**Models are reasoning engines and usually do a pretty good job of it, and Agentic Studio already gives the chat tools to work with.** I didn't tick any tools for this run, but Studio's built-in tools (Sites, Content, Pages and Web Search) were still available, and the chat used them without being asked.

I ended up using six natural language prompts. With them, the chat found the page, searched the web for Google's current guidance on titles, descriptions and structured data, and graded each field. It then drafted all five fields with valid JSON-LD, wrote them to the CMS behind Studio's own Apply changes card, and read them back, all without an agent or any configuration.

The recommendations were OK. From the starting values, seo-jev-analyzer's metadata score went from 0.00 to 2.46, and the page score from 4.27 to 4.90.

| What the stage 1 run wrote | 2.46     | 4.90 |

### What the prompts did well

Looking back over the six prompts, these habits did most of the work:

- **A role.** "Act as an SEO specialist."
- **The goal stated as an outcome.** "Be the page a search engine or AI answer engine cites when someone in Adelaide asks how much a casual bouldering session costs."
- **Research on demand.** "Use web search to find Google's current guidance on title links, meta descriptions and structured data." Any AI with web search can do this, not just SitecoreAI. But the chat has to look up what good looks like every time, which adds up to a lot of repeated time and tokens, and it can interpret the same guidance differently each time.
- **Exact fields and an exact output shape.** The five fields by name, read from the content item, a table with character counts, and the JSON-LD in a code block.
- **A way to say "I don't know".** "Write EMPTY for a field that exists with no value and NOT RETURNED for a field your tools did not give you." Some tools leave fields out, and without this the chat fills the gap with a guess.
- **Rules with numbers.** A title of 60 characters or fewer, a description of 150 to 160, ending with the site name.
- **Facts bounded to the source.** "Use only prices, times and facilities from the page."
- **The job in rounds.** Get, analyse, suggest, review, apply, re-check, with "do not change anything" in every round until the one that applies.
- **A review round that names its checks.** Count the characters, confirm every fact against the page, and confirm the JSON-LD is valid.

A plain chat gets a long way, but it doesn't get there the same way each time.

## Inconsistent: same prompt, different work

**The same prompt, sent twice, can produce different work, and the chat can't reliably tell you when its own work is wrong.** You won't see most of this in a single run; it shows up across runs.

**It picks its own tools.** In the recorded run, Round 1 used six tools nobody asked for: tool search, list sites, search pages, get page, get page metadata and get page HTML. Another run of the same prompt chose a different set. Different tools return different fields, ask for approval differently and write by different routes. I saw this in every run, but I haven't tested how often each path comes up.

**It misses things.** In my experience, about one run in ten doesn't pick up some of the fields it was asked to analyse.

**It gets lazy in a long session.** Run it too many times in the same chat and it starts reusing data from earlier instead of fetching it again.

**It misjudges its own result.** In Round 6 it read the five fields back from the content item, by field name, but its tools returned only two of them. It scored the other three 0/10 as NOT RETURNED and called the update "partially applied". The Content Editor held all five, exactly as proposed.

**It marks its own work.** Scores out of 10 and character counts come from the chat, with nothing outside to check them. Round 3's counts were right: 50 characters for the title and 159 for the description. Round 4, the self-check, changed no values. Its only correction was to the length of the minified JSON-LD, from 348 characters to 349. It's 348, so the check added an error.

**Guardrails are only requests.** "Do not guess", "do not invent anything", "check your proposal against every rule": the model acts on them as it chooses, and nothing confirms it obeyed.

**Warnings slip past.** The Apply changes card appeared because of the tool the chat happened to pick; with another tool it asks in words instead. After the save, Studio reported that the changes "could not be fully applied". The Content Editor showed all five fields saved exactly as proposed, with every other field untouched. The warning was wrong, and nothing in the chat says so.

## Tedious: the price of reliability by hand

**Nothing in a plain chat makes the result reliable, so the person does it, every time.**

A good share of the text in the prompts is guardrails rather than the task itself: what the chat can and can't do, don't guess, don't change anything, check your work. The same lines go into prompt after prompt, because a plain chat has nowhere else to keep them.

## Stage 2: Context Engineering

Next, we move on to Context Engineering. The popular definition of this stage is that, instead of stating everything in the prompt, we point the agent to information and it adds that to the prompt itself.

On its own, this technique doesn't improve our SEO results. The improvements come when we point the agent at knowledge that is much more detailed, and that someone has spent much more time curating.
