An agent used to be one big prompt: who it is, what it knows, what it does and how it does it, all in one place. That's no longer how I build them.

What an agent does and knows now belongs in [skills](/blog/sub-agents-vs-personas-vs-skills-a-journey-through-code-architecture), loaded when the task needs them. How it does the work is set up in the harness, on the tools: the hooks, scripts and checks that run whether the agent remembers them or not. What's left for the agent definition itself is **how it thinks**, and that's what this post is about.

Most agent teams are org charts: a coder, a reviewer, a planner, maybe a security specialist. You assign a function, give it a prompt and wire them together. It's the same structure as a human dev team, just faster and cheaper.

I built my first agent team this way. It worked the way org charts always work. Everyone did their job, and nobody did the thinking that falls between jobs. The frontend agent wrote components. The review agent checked them. Neither one stopped to ask whether the component should exist at all.

I don't think the agents were the problem. The composition model was. Functional decomposition tells you _what_ each agent does, but it says nothing about _how_ each agent thinks, and the "how" is what decides whether the team produces mechanical output or considered work.

## Cognitive profile is the useful axis

When I started treating agents as cognitive profiles rather than functional roles, the team changed.

A functional label says "frontend-dev writes React components." A cognitive profile says "frontend-dev defaults to implementation-mode thinking, with a low weighting toward first-principles reasoning." That second description tells you something about the agent's decision boundaries: when it should act, when it should escalate, and what kind of problem it's suited to handle.

I wrote about [three dimensions of agent context](/blog/three-dimensions-of-agent-context-from-over-engineering-to-orthogonal-design) previously: posture, standards and specialist knowledge. Cognitive profile sits in that first dimension. It isn't what the agent knows. It's the shape of the agent's thinking, and it decides how the agent _uses_ what it knows.

## Borrowed from Deloitte, applied to agents

This isn't a new idea. Deloitte's [Business Chemistry](https://www.deloitte.com/us/en/services/consulting/services/business-chemistry.html) framework classifies people into four working styles: Pioneer (possibility-oriented, big-picture), Guardian (stability-oriented, detail-driven), Driver (challenge-oriented, results-focused) and Integrator (connection-oriented, consensus-building).

Everyone is a blend, with a primary and a secondary. The model doesn't box people into types. It describes their default cognitive stance and the traits they fall back on under pressure.

I've found agent teams work the same way:

- My **architect agent** leads with first-principles reasoning. It questions assumptions, decomposes problems and challenges the brief before anything gets built. Pioneer-Driver blend.
- My **frontend-dev** leads with implementation. It builds what's specified, follows established patterns and ships code. Guardian-Driver blend.
- My **code reviewer** leads with evaluation. It checks consistency against project conventions and catches drift from agreed patterns. Guardian-Integrator blend.
- My **security auditor** leads with adversarial thinking. It traces data flows and looks for what could break. Guardian with a Driver secondary.

These are different cognitive shapes, not different levels of capability. The reviewer isn't a lesser architect, and the developer isn't a lesser reviewer. They're weighted differently because the work needs different default modes.

That matters most when the work needs a thinking mode the current agent isn't weighted toward.

## Traits are weighted, not binary

Every agent has every trait. The weighting sets the default, not the boundary.

My architect agent has first-principles reasoning weighted at around 85%. That's its primary mode: when it's uncertain, it reasons from fundamentals. My frontend-dev has the same trait weighted at around 20%. It _can_ reason from first principles, but it shouldn't default to it, because most of its work is implementation where [first-principles thinking](/blog/first-principles-in-agent-conversations-when-to-stop-accommodating-and-start-reasoning) would be expensive overhead.

That 20% is still doing real work. It gives the frontend-dev the capacity to recognise when implementation-mode thinking isn't enough: when the component structure doesn't fit the data shape, when the state management pattern is fighting the feature requirements, or when what was asked for doesn't match what the codebase actually needs. The developer doesn't resolve these. It recognises them, and that recognition is the trait doing its job at 20%.

## Same skill, different thinking

This is where the split between skills and profiles shows up. Give four agents the same skill and the same prompt, and they don't do the same work. The skill tells each of them how to build an atomic component. Their profile decides what they notice first, and what they never think to question.

An implementer will see the prompt and drill down, but it won't stop to ask whether the component should be there at all. That's not a flaw in the skill, and it's not a flaw in the agent either. It's the profile doing exactly what it was weighted to do.

There's a benefit in this too. When every agent references the same skill, we get a level of consistency we may not have had before, because all of them are working off the same context. They're simply applying it, or thinking about it, in a different way - the way they should.

## Escalation is a reasoning-mode hierarchy

This is where composition by cognitive profile pays off. When the frontend-dev hits a problem that exceeds its first-principles weighting, the work flows to the agent with a higher weighting of that trait. That isn't the developer failing. It has correctly identified that the moment needs a different cognitive mode.

The escalation pattern maps to the trait hierarchy:

- **Implementation uncertainty:** peer consult. Another agent with similar weighting and different domain knowledge.
- **Design uncertainty:** architect. Higher first-principles weighting.
- **Requirement uncertainty:** human gate. No agent has enough context.

Each tier matches the kind of thinking the problem needs. Peer consultation answers "how do I build this?" Design escalation answers "should I build this?" Human gates answer "what are we actually trying to do?"

The 20% first-principles weighting in the developer is what makes the chain work. Without it, the developer would implement its way through design problems, producing code that technically runs and architecturally misses. The weighting doesn't give the developer the answer. It gives it the self-awareness to stop.

## The orchestrator problem

The hardest agent to define is the one that decides which cognitive profile the moment needs: whether it needs someone to build, someone to question or someone to decide. I don't have this solved, though I think of it as the Integrator in Deloitte's model, optimised for the transitions between modes rather than any one of them.

I also don't think the problem is as severe as I used to make it sound. When people filled these roles, the delivery lead or the lead architect was still a person who could make mistakes and judgement calls. The point of an orchestrator isn't to be flawless. It's to bring consistency to those line-call decisions, and to be the place where the buck stops. In practice, I've used Claude Fable or Opus for it, especially since the 5 releases.

## The pattern

Define an agent by how it thinks. Put what it does and knows in skills, and how it does it in the harness. Then compose the team by thinking profile: give every agent every trait at different weightings, let the weightings set defaults and escalation boundaries, and build the hierarchy around reasoning modes rather than reporting lines.

Your agents, your weightings, your boundaries. The idea is that cognitive profile is the useful composition axis. How you apply it is yours.
